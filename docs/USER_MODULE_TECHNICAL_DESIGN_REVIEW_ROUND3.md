## 1. 复审结论

本轮更新准确回应了第二轮提出的全部问题，并且不是简单补文字，而是把机制落到了可执行规则：

- `/auth/csrf` 明确要求按数据库中的有效 Session 判定认证上下文，失效会话按匿名处理；数据库读取异常不得静默降为匿名。
- 管理员重置密码的威胁模型已在权限模型和第 12 节明确：管理员可接管账号，系统不提供对恶意管理员的数据机密性保护。
- 登出流程明确了 Session Cookie、匿名 CSRF Cookie、前端重新获取令牌的完整顺序，并说明旧认证令牌不承诺永久可重放。
- 多标签页增加了 `BroadcastChannel`、focus/visibility 复核、请求代次丢弃和服务端 `X-Expected-User-ID` 四层机制。
- SQLite 事务生命周期写成了固定模板，包括独立的回滚超时上下文和 `driver.ErrBadConn` 丢弃连接；该方式与 Go 标准库 `database/sql.Conn.Raw` 的释放逻辑一致。
- 幂等记录明确落在 `meal_logs`，并给出字段、唯一约束和“一次确认一条记录”的边界。
- 上轮 P2 中的 Cookie `Max-Age`、`excluded_foods.status`、临时密码文件、CLI 用户名规范化和 `/auth/*` no-store 均已补齐。

**当前没有 P0/P1 问题。** 文档可以作为实现基线；剩余事项不改变架构，建议在冻结 API 契约前处理 R3-01、R3-02、R3-04，其余可在实现中补齐。

## 3. 剩余事项

### R3-01（P2）`X-Expected-User-ID` 的契约位置、取值时点和 409 处理

**位置**：`:256`、`:279-281`、`:183`、`:232`

**现状**

- `6.3` 规定所有要求登录的写接口必须带 `X-Expected-User-ID`；
- 值为“表单加载或操作发起时的用户 ID”；
- 与 Session 用户 ID 不同返回 `409 IDENTITY_CHANGED`；
- 前端通过 `api.js` 统一发送；
- 公开注册、登录及幂等退出不要求该 Header。

**需要明确**

1. **契约位置**：Header 是全局写请求约定，但只写在 `6.3`，第 5 节 API 表和认证接口表没有提及。建议在 `5` 节开头增加一条全局规则，并说明 `409 IDENTITY_CHANGED` 的客户端处理，避免后端和前端各自理解。
2. **取值时点**：Header 必须绑定到页面/表单渲染时的身份快照，而不是请求发送时从全局状态读取的当前用户 ID。否则，一个已经刷新为“用户 B”的旧页面在提交用户 A 的表单时，会带上用户 B 的 ID 并通过校验。文档已有“客户端不能在重提旧表单时把此值自动替换为新账号”，建议进一步明确：`api.js` 不应在发送时读取当前全局身份，表单/操作必须携带其创建时的身份快照。
3. **409 前端处理**：前端应在收到 `409 IDENTITY_CHANGED` 时丢弃当前表单、重新调用 `/me`、进入对应页面，而不是用同一份旧表单重试。当前 `:281` 的“身份检查失败时保持暂停提交，提供重试”容易被理解为重试旧表单。
4. **登出例外**：`POST /auth/logout` 不要求 Header。若标签页 A 停留在旧账号，标签页 B 已切换到新账号，A 的登出请求在拿到新会话的 CSRF 令牌后可能登出新账号。CSRF 绑定和广播机制已显著降低该风险；建议在文档中说明这是接受的边界，或要求登出也带 Header（代价是登出在身份不明时不能直接完成）。

**建议补充测试**

- 缺失、非数字、负数、超长 `X-Expected-User-ID` 返回 400；
- 身份切换后旧表单携带旧 ID 返回 409，且无任何业务写入；
- 全局身份已更新为 B、旧页面仍携带 A 的快照时返回 409；
- 前端收到 409 后不重试旧表单，而是重新加载身份。

### R3-02（P2）登录流程的复核字段与 4.2 不一致

**位置**：`:132`、`:248`

**现状**

- `4.2` 要求登录/改密写事务“再次确认状态、版本和原密码哈希未变化”；
- `6.2` 的登录流程只写“事务复核状态及版本”。

**问题**

原密码哈希复核是防止“旧密码校验完成后恰逢管理员重置，仍签发会话”的关键不变量。流程章节省略该字段，容易被实现者漏掉。

**建议**

将 `:248` 改为“事务复核状态、`auth_version` 和原密码哈希未变化 → 创建 Session”，并增加并发测试：密码验证完成后、创建 Session 前执行管理员重置，登录必须返回 401 且不创建 Session。

### R3-03（P2）单进程假设缺少强制手段

**位置**：`:156-164`、`:389`

**现状**

文档多处依赖“同一部署只运行一个服务进程”：

- `SetMaxOpenConns(1)` 的写串行化；
- 内存限流器；
- CSRF 密钥文件复用；
- 启动清理和会话清理任务；
- CLI/迁移要求停服务。

但没有启动锁或进程检测。两个进程同时运行时，限流额度会叠加，清理任务可能重复，SQLite 写入竞争依赖 `busy_timeout` 而不是设计保证。

**建议**

增加数据库目录锁文件（例如 `data/server.lock`，启动时独占加锁，失败退出）或在启动时检测已有服务进程。至少要在运维文档中把“单进程”写成硬性前置条件，并在 `admin init`/迁移命令中检查锁。增加测试或启动检查：第二个进程必须启动失败并给出明确错误。

### R3-04（P2）私有业务数据的缓存策略未覆盖

**位置**：`:152`

**现状**

`Cache-Control: no-store` 覆盖 `/auth/*`、身份、设置和管理响应，但没有明确库存、私有食谱、饮食记录、营养统计等业务数据响应。

**风险**

这些响应包含用户私有数据。即使它们不在用户模块的 API 表内，也应遵循同一原则，避免被浏览器或中间缓存保存。公共食谱/食材可以缓存，但需要明确与私有数据的区分。

**建议**

把规则改为“所有返回当前用户私有数据的响应一律 `Cache-Control: no-store`”，并在各业务模块的验收项中复用；公共数据如要缓存，单独声明 `Cache-Control: public` 或 `private` 策略。

### R3-05（P2）幂等重放响应与 `meal_logs` 可变性

**位置**：`:260-266`

**现状**

文档规定 `meal_logs.id` 是重放返回的结果标识，但没有定义：

- 重放响应是只返回 `meal_logs` 记录，还是完整重建首次响应（包括库存变化等）；
- `meal_logs` 创建后是否允许修改；
- 如果允许修改，重放是返回首次结果还是当前记录。

**建议**

明确首版 `meal_logs` 创建后不可变（append-only），重放返回 `meal_logs.id` 及该记录的完整快照；不承诺重建首次响应中的临时字段（如库存剩余量）。如果未来支持编辑饮食记录，需要单独定义重放语义或保存首次响应快照。

### R3-06（P3）哈希队列的容量与等待上限

**位置**：`:121`、`:149`、`:228`

**现状**

文档规定最多同时执行 2 个哈希任务、队列满返回 429，但没有给出队列容量、单次等待上限或超出后的清理策略。

**建议**

明确有界队列（例如最多等待 32 个任务）、最大等待时间（例如 5 秒）和 `Retry-After` 建议值；队列满时快速失败，不能无限堆积。增加并发测试：超过并发和队列上限时返回 429，且没有 goroutine 泄漏。

### R3-07（P3）停用食材的跨模块行为

**位置**：`:106`、`:191`、`:92`

**现状**

`foods.status` 已定义为 `active`/`disabled`，并明确停用后保留历史关联、已有忌口继续有效。但没有说明：

- 新增库存是否只能选择 active 食材；
- 公共食谱或私有食谱是否还能新增/保留停用食材；
- 推荐是否排除含停用食材的食谱，还是继续展示但标注；
- `excluded_food_ids_json` 中存在但 `foods` 表已无对应行时如何展示（当前 `status` 只有 active/disabled）。

**建议**

在跨模块验收中明确：库存新增只接受 active 食材；已有记录保留；食谱标注停用食材；推荐对停用食材采取“保留但提示”或“排除”的明确策略；缺失食材行按数据异常处理，不静默当作正常食材。`excluded_foods` 可增加 `missing` 状态，或在读取时返回 500 并记录数据完整性错误。

### R3-08（P3）其余小项

| 项目 | 建议 |
| --- | --- |
| 普通改密新旧相同 | 除强制改密不得沿用临时密码外，建议普通 `PUT /me/password` 也拒绝新密码等于当前密码，减少无意义变更和审计噪声。 |
| `503 DATABASE_BUSY` 前端提示 | 在 `7` 节明确提示“本次操作未保存，请稍后重试”，避免用户误以为数据已写入。 |
| CSRF 密钥丢失恢复 | `:148` 要求丢失时拒绝启动，建议补充操作步骤：停止服务、确认备份、生成新密钥（所有 CSRF 令牌失效，Session 不受影响）、启动并验证登录。 |
| CSP 与内联样式 | `:168` 要求前端不使用内联样式；Vue 的 `:style` 会生成内联 style 属性，被 `style-src 'self'` 阻止。建议增加 lint 规则或验收检查，禁止 `:style`/内联 style。 |
| 错误响应字段 | 建议明确错误码 `IDENTITY_CHANGED` 的 message 面向用户展示，不包含内部用户 ID 差异等细节。 |

## 4. 建议补充的测试

| 范围 | 场景 |
| --- | --- |
| 身份断言 | `X-Expected-User-ID` 缺失/非法/旧值；旧页面在全局身份更新后仍携带旧快照；409 后不重试旧表单；登出边界 |
| 登录竞态 | 密码验证完成后、Session 创建前发生重置或禁用，登录失败且不创建 Session |
| 单进程 | 第二个服务进程或 `admin` 命令在锁被占用时启动失败；锁释放后可正常启动 |
| 缓存 | 库存、私有食谱、饮食记录、营养统计等私有响应均为 `no-store`；公共数据策略明确 |
| 幂等重放 | 重放响应结构与首次一致；`meal_logs` 不可变；手动记录幂等字段为空 |
| 哈希队列 | 并发上限、队列上限、等待超时、429 与 `Retry-After`、无泄漏 |
| 停用食材 | 库存新增拒绝停用食材；已有记录保留；推荐策略一致；缺失食材行处理 |
| 运维 | `503` 前端提示；CSRF 密钥丢失后的恢复流程；CSP 阻止内联样式 |

## 5. 最终结论

本轮更新已经解决了上轮全部阻断和重要问题，**方案可以进入实现阶段，无需再调整架构**。

建议在冻结 API 契约前完成三项：

1. **R3-01**：把 `X-Expected-User-ID` 写入第 5 节全局约定，明确取值时点为页面/表单加载时的身份快照，并定义 `409 IDENTITY_CHANGED` 的前端处理。
2. **R3-02**：统一登录流程与 `4.2` 的复核字段，补上原密码哈希复核。
3. **R3-04**：把 `no-store` 扩展到所有私有业务数据响应。

R3-03 建议在部署前实现启动锁；R3-05 至 R3-08 可作为实现 checklist，不阻塞编码启动。
