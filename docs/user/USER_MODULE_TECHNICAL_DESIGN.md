# FreshPlate 用户模块完整实现技术方案

本文将用户模块从本地单人设置扩展为注册登录、会话管理、角色权限、个人设置和业务数据隔离，是后续编码与验收依据。当前仓库只有实施方案，本文中的目录、接口和表结构均为待实现设计。

## 1. 目标与边界

### 1.1 首版交付

- 用户名和密码注册、登录、退出、登录状态恢复。
- 修改密码、管理员重置密码、首次重置后强制改密。
- 普通用户和管理员两个固定角色，账号启用与禁用。
- 个人饮食限制和营养目标设置。
- 库存、私有食谱、饮食记录、营养统计按用户隔离。
- 用户管理页面、关键管理操作审计、管理员初始化命令。
- 数据迁移、自动化测试、部署说明和人工验收。

首版不实现第三方登录、短信/邮箱验证、自助找回密码、自定义角色、权限编辑器、家庭共享、账号删除及多因素认证。无邮箱找回时，普通用户通过管理员重置密码恢复访问；最后一个管理员丢失密码时，通过服务器本地恢复命令处理。

### 1.2 运行方式

继续使用 Go 1.26.4、Gin、`database/sql`、`modernc.org/sqlite`、Vue 3 和 Vite。角色和权限用代码中的固定规则表达，不增加权限框架、ORM、Redis 或 JWT。

开发环境通过 Vite `/api` 代理访问后端；部署时前端与 API 使用同一站点，不启用 CORS。首版仍默认监听环回地址。完成认证、隔离和安全验收后，才可以通过 HTTPS 反向代理提供网络访问；具备多用户能力不等于自动开放公网。

首版采用公开注册：能够访问站点的人可以注册普通账号，不能通过注册获得管理员角色。暂不增加注册开关和邀请码；若部署要求仅限受邀用户，应先调整注册策略再开放访问。

## 2. 权限模型

| 能力 | 未登录 | 普通用户 `user` | 管理员 `admin` |
| --- | --- | --- | --- |
| 注册、登录、获取 CSRF 令牌 | 允许 | 允许 | 允许 |
| 读取本人身份、修改本人密码 | 禁止 | 允许 | 允许 |
| 退出（幂等清理，须有效 CSRF） | 允许 | 允许 | 允许 |
| 管理个人设置、库存、饮食记录和营养统计 | 禁止 | 仅本人 | 仅本人 |
| 查看已发布的公共食谱、公共食材 | 禁止 | 允许 | 允许 |
| 创建及管理私有食谱 | 禁止 | 仅本人 | 仅本人 |
| 维护公共食材、公共食谱 | 禁止 | 禁止 | 允许 |
| 用户列表、启停账号、变更角色、重置密码 | 禁止 | 禁止 | 允许 |
| 查看管理审计记录 | 禁止 | 禁止 | 允许 |

管理员没有直接查询他人饮食记录、库存、过敏信息或私有食谱的接口权限；这不构成对恶意管理员的隔离。管理员能够设置目标账号的临时密码，随后登录并改密即可接管账号、访问其数据。首版将拥有重置权限的管理员纳入可信边界，以审计追踪操作；强制改密不能阻止管理员接管，详见第 12 节。注册请求不得指定角色或状态；出现这些字段直接返回参数错误。

后端对权限作最终判断。Vue 路由守卫和隐藏按钮仅用于交互。资源查询同时约束资源 ID 与当前用户 ID，不能先按 ID 取出数据再依赖前端检查。

## 3. 数据模型

除 `sessions` 使用令牌摘要作为非空主键外，其余表使用 SQLite 整数主键；`user_preferences` 以用户 ID 为主键。时间存 UTC Unix 秒，接口输出 RFC 3339 UTC 字符串。所有连接启用外键，写入使用事务；限制字符串长度和状态取值。账号不支持物理删除，用户归属外键采用 `ON DELETE RESTRICT`。

### 3.1 `users`

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `id` | INTEGER PRIMARY KEY | 用户 ID |
| `username` | TEXT NOT NULL UNIQUE | 去除首尾空白后转小写；3～32 个 ASCII 字母、数字或下划线 |
| `password_hash` | TEXT NOT NULL | 带算法版本、参数、盐和结果的 Argon2id 编码 |
| `role` | TEXT NOT NULL，CHECK IN ('user','admin') | 注册默认 user |
| `status` | TEXT NOT NULL，CHECK IN ('active','disabled') | 默认 active |
| `must_change_password` | INTEGER NOT NULL，CHECK IN (0,1) | 默认 0，管理员重置后为 1 |
| `auth_version` | INTEGER NOT NULL DEFAULT 1 | 撤销会话及防止并发登录使用旧密码结果 |
| `created_at` / `updated_at` | INTEGER NOT NULL | 创建、修改时间 |

用户名首版不可修改。用户名唯一性以数据库约束为准，不能仅用注册前查询处理并发重复注册。密码哈希不出现在任何响应、日志或审计详情中。

### 3.2 `sessions`

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `token_hash` | BLOB NOT NULL PRIMARY KEY，CHECK length = 32 | 32 字节随机令牌的 SHA-256 摘要 |
| `user_id` | INTEGER NOT NULL REFERENCES users(id) | 归属用户 |
| `auth_version` | INTEGER NOT NULL | 创建时用户认证版本 |
| `created_at` | INTEGER NOT NULL | 创建时间 |
| `expires_at` | INTEGER NOT NULL | 固定 7 天到期，不自动续期 |

建立 `sessions(user_id)`、`sessions(expires_at)` 索引。原始令牌使用 `crypto/rand` 生成并编码为 base64url，只通过 Cookie 交给浏览器。服务端重启后会话继续有效；过期数据由启动时及每小时清理，查询始终检查到期时间，不依赖清理任务判断有效性。

### 3.3 `user_preferences`

| 字段 | 类型/约束 | 说明 |
| --- | --- | --- |
| `user_id` | INTEGER PRIMARY KEY REFERENCES users(id) | 每用户一条 |
| `allergens_json` | TEXT NOT NULL DEFAULT '[]' | 固定过敏原编码数组 |
| `excluded_food_ids_json` | TEXT NOT NULL DEFAULT '[]' | 公共食材 ID 数组，保留已有停用食材引用 |
| `dietary_preferences_json` | TEXT NOT NULL DEFAULT '[]' | 固定饮食偏好编码数组 |
| `daily_energy_kcal` | REAL，可空 | 参考能量，0 < 值 ≤ 20000 |
| `daily_protein_g` | REAL，可空 | 参考蛋白质，0 < 值 ≤ 2000 |
| `daily_fat_g` | REAL，可空 | 参考脂肪，0 < 值 ≤ 2000 |
| `daily_carbohydrate_g` | REAL，可空 | 参考碳水，0 < 值 ≤ 2000 |
| `updated_at` | INTEGER NOT NULL | 修改时间 |

以上数值范围只是输入保护，不代表推荐摄入量。拒绝非有限数值。数组去重，过敏原和偏好各最多 32 项，忌口最多 500 项。JSON 数组由应用验证并整体保存，不依赖 JSON 内部外键。

食材停用不等于用户撤销忌口：被引用食材不物理删除，读取时保留 ID 和名称，推荐与烹饪确认继续执行限制。新增忌口只能选择 active 公共食材；保存时允许保留该用户原有的停用食材 ID，拒绝不存在的 ID 及新增停用项。前端标注停用状态但不自动移除；只有用户显式移除并保存后才解除限制。校验和保存使用同一事务，防止并发停用或设置修改绕过规则。

过敏原初始编码为 `milk`、`egg`、`fish`、`crustacean`、`mollusc`、`peanut`、`soy`、`wheat`、`tree_nut`、`sesame`；偏好为 `vegetarian`、`vegan`、`low_salt`。名称与编码由前后端共享契约，扩展时同步食谱标注和测试。未列出的特殊过敏需求不能宣称已覆盖。偏好只是排序依据，过敏和忌口必须填写在强制限制中。

注册时与用户创建在同一事务中插入默认设置。读取时若记录缺失，视为数据异常并返回错误，不能解释为无饮食限制。

### 3.4 `audit_logs`

字段包括 `id`、`actor_user_id`（本地命令时可空）、`actor_source`（`web`/`cli`）、`action`、`target_user_id`、`details_json`、`created_at`。按创建时间和目标用户建立索引。

记录管理员初始化、角色变更、启停账号、管理员重置密码和本地恢复。详情仅保存角色/状态的前后值，不保存新旧密码、密码哈希、Cookie、会话令牌、过敏信息或完整请求体。管理变更和审计写入同一事务，审计失败则变更回滚。审计接口只读，不提供网页修改或删除入口。首版长期保留，不自动清理；运维定期检查数据库和备份体积，后续按实际增长量制定归档策略。

### 3.5 业务表联动

- `foods.status` 取值为 `active` 或 `disabled`，默认 active。停用后保留食材 ID、名称及历史关联，已有忌口继续有效；不提供物理删除入口。
- `inventory_items`、`meal_logs` 增加非空 `user_id` 外键；按 `(user_id, id)`、`(user_id, meal_time)` 等实际查询建立索引。
- `recipes` 增加 `owner_user_id`（可空）和 `visibility`（`private`/`public`）。数据库约束为 private 时 owner 非空、public 时 owner 为空。公共食谱由管理员独立创建、维护和发布；私有食谱只能由所有者访问，管理员不能读取或发布他人的私有食谱。首版不提供私有转公共、投稿或审核流程。AI 新生成食谱默认私有。
- `recipe_ingredients`、`recipe_allergens` 通过父食谱校验访问权限，不能凭子记录 ID 越权。
- 公共食材与公共食谱不绑定个人偏好。推荐候选仅包含已发布公共食谱和当前用户私有食谱。
- 烹饪确认事务内验证所有库存归属和食谱可见性后再扣减、记餐；幂等键唯一约束按 `(user_id, idempotency_key)` 建立。
- 饮食记录保存当时的名称、份量和营养快照；食谱修改、设置变化不改写历史数据。

## 4. 密码、会话及请求安全

### 4.1 密码处理

- 密码为 12～128 个 Unicode 码点，同时限制 UTF-8 编码不超过 512 字节；拒绝无效 UTF-8，按原始 UTF-8 字节哈希和验证，不做 NFC/NFKC 规范化、不裁剪空白、不改变大小写、不强制字符组合。视觉相似但码点不同的密码视为不同密码。
- 使用 `golang.org/x/crypto/argon2` 的 Argon2id；初始参数 memory=64 MiB、iterations=3、parallelism=1，随机盐 16 字节、结果 32 字节。
- 使用常量时间比较；解析哈希时限制编码长度及参数上限，损坏哈希按认证失败处理并记录不含敏感值的内部错误。
- 在部署机器上测量哈希耗时和内存；默认最多同时执行 2 个哈希任务，队列满时返回 429。未知用户名也校验预生成的等成本虚拟哈希。
- 依赖锁入 `go.mod`/`go.sum`。不自行设计密码算法或加密存储可逆密码。

### 4.2 会话生命周期

登录成功生成全新 Session。HTTPS 部署的 Cookie 名称为 `__Host-freshplate_session`，设置 `Secure`、`HttpOnly`、`SameSite=Lax`、`Path=/` 和 `Max-Age=604800`（7 天），不设置 Domain。本地 HTTP 开发使用 `freshplate_session` 并关闭 Secure，开发与生产配置不能混用。

首版采用固定 7 天有效期，不续期、不做空闲超时或定期轮换，也不限制每用户同时在线会话数。每次登录生成新令牌，角色变更不要求重新登录，以每次请求读取的当前角色为准。

认证中间件联合查询 Session 和用户，校验有效期、active 状态及 `auth_version`，每次读取当前角色，不缓存角色权限。禁用、改密、重置密码时增加 `auth_version` 并删除该用户全部 Session。

密码哈希在数据库写事务之外执行。完成校验后，登录/改密写事务再次确认状态、版本和原密码哈希未变化，避免“旧密码校验完成后恰逢重置，仍签发有效会话”。账号状态变更与会话撤销在同一事务内完成。

退出通过 CSRF 检查后删除当前 Session，以同名、同 Path、同 Domain 策略的 `Max-Age=0` Cookie 清理浏览器会话（Go Cookie 使用 MaxAge=-1），并签发新的匿名 CSRF Cookie；204 无响应体，前端清空内存令牌后调用 `/auth/csrf` 获取新值。已退出或会话失效时，在获取有效匿名令牌后重复退出仍返回 204；持有旧认证 CSRF 的重复请求允许先返回 CSRF_INVALID，不承诺旧令牌永久可重放。普通改密需要当前密码；成功后清理所有会话和 Session Cookie、签发匿名 CSRF Cookie，前端重新获取令牌后进入登录页。强制改密账号登录后仅可访问身份查询、退出、修改密码和 CSRF 接口，其余接口返回 `403 PASSWORD_CHANGE_REQUIRED`。

### 4.3 CSRF、来源及限流

- CSRF Cookie 名称为 HTTPS 下的 `__Host-freshplate_csrf`，本地 HTTP 下为 `freshplate_csrf`；设置 HttpOnly、SameSite=Lax、Path=/、不设置 Domain，HTTPS 下设置 Secure。令牌包含随机数、签发时间及 HMAC-SHA256 签名，有效期 24 小时；新签发 Cookie 的 Max-Age=86400，复用时不延长签名时效。
- `/auth/csrf` 与写请求校验共用认证上下文解析：只有数据库中 Session 存在、未过期、用户 active 且 auth_version 匹配时，才视为已认证；不能仅凭 Cookie 存在或 CSRF 的 HMAC 正确判断身份。must_change_password 不使 Session 失效，仍使用已认证上下文及对应接口白名单。
- 缺失、格式错误、不存在、已过期、被撤销或版本不匹配的 Session 均按匿名上下文处理，并清理遗留 Session Cookie。`/auth/csrf` 此时不复用旧认证令牌，只复用有效匿名令牌或签发新匿名令牌，允许重新登录。数据库读取异常必须返回 500/503，不得静默降为匿名。
- 已认证令牌的签名输入包含有效 Session 的 token_hash，匿名令牌使用不同的用途标记，两者不得互用。匿名上下文仍可访问注册、登录及幂等退出，但受保护业务接口返回 401。Session 在获取令牌后才失效的竞态按 CSRF_INVALID/401 处理，前端重新获取，不自动重放。
- `GET /api/auth/csrf` 返回 `{token}` 并使用 `Cache-Control: no-store`。若 Cookie 中令牌有效、未过期且与当前认证上下文匹配，复用该值；否则生成、设置 Cookie 并返回。响应不得启用跨域读取。
- 前端将令牌保存在内存，所有 POST/PUT/PATCH/DELETE 请求用 `X-CSRF-Token` 发送；后端校验签名、用途、Session 绑定、时效及 Header/Cookie 一致性，签名使用常量时间比较。CSRF 失败必须发生在业务变更之前。
- 登录成功轮换 CSRF 令牌并在登录响应中返回 `csrf_token`，前端更新内存。其他标签页遇到 `CSRF_INVALID` 时重新获取令牌、更新内存，再提示用户重新提交，不自动重放写请求。并发首次获取发生 Cookie 覆盖时同样按此流程恢复。
- 注册、登录、退出同样校验 CSRF。所有写请求必须带 Origin，精确匹配配置的 scheme、host、port；缺失、null 或不匹配均返回 `403 CSRF_INVALID`，不能从 Host 或 X-Forwarded-* 推导允许源。GET 不强制携带 Origin，且不得改变业务数据。
- 有 JSON 请求体的接口只接受解析后媒体类型为 application/json 的 Content-Type（允许 charset=utf-8 参数），否则返回 415。无请求体的退出接口允许不带 Content-Type；不得以表单、text/plain 等方式绕过写请求检查。
- CLI 不暴露网络旁路，直接以本地运维权限执行相同账号规则和审计；HTTP Origin/CSRF 中间件不适用于 CLI。
- HMAC 密钥首次初始化生成 32 个随机字节，保存在仓库外或被忽略的 `data/` 文件，权限 0600；多次启动复用。丢失时拒绝启动，不静默换密钥。
- 单进程内存限流：登录每 IP 15 分钟 30 次、每规范化用户名 15 分钟 10 次；注册每 IP 每小时 10 次；修改密码每用户 15 分钟 5 次、每 IP 15 分钟 20 次。计数包含成功和失败请求，账号存在与否规则一致；限流先于密码哈希执行，返回 429 与 Retry-After，不做永久锁号。限流与哈希队列满统一使用 RATE_LIMITED，内部指标区分原因，不记录密码。
- 限流记录按过期时间清理并限制最大键数，达到上限时拒绝新增认证请求，不能无限占用内存。读取和更新并发安全；限制器重启会清空，未来多实例部署时再改为共享存储。
- Gin 禁止信任任意代理提供的客户端 IP；使用反向代理时仅信任明确配置的代理地址。
- `/auth/*`（包括成功和错误响应）、身份、设置和管理响应均使用 `Cache-Control: no-store`；请求体上限 64 KiB，拒绝未知字段和尾随 JSON。日志不记录认证请求体与 Cookie。

### 4.4 SQLite 连接及事务策略

首版单个服务进程打开数据库，连接池设置 `SetMaxOpenConns(1)`、`SetMaxIdleConns(1)`。连接初始化对每个连接执行 `PRAGMA foreign_keys=ON`、`PRAGMA busy_timeout=5000`；打开数据库时启用 WAL 并检查返回模式。使用驱动支持的逐连接初始化方式，不能只在池中任取一条连接执行一次。驱动版本在实施时锁定，初始化参数必须通过临时文件集成测试验证。

涉及先检查后写入的操作（登录签发会话、改密、管理变更、初始化、烹饪确认、设置保存）统一在数据访问层获取专用 `*sql.Conn`，执行 `BEGIN IMMEDIATE`，后续查询及写入全部使用该连接，成功 COMMIT，失败 ROLLBACK，最终归还连接。不在事务内部通过 `*sql.DB` 获取第二条连接，也不混用 `sql.Tx` 与手写事务。哈希计算、外部模型调用不占用写事务。

不依赖尚未验证的驱动 DSN 事务参数。锁等待超过期限时回滚并返回 `503 DATABASE_BUSY`，不忽略错误或在事务外继续更新；首版不自动重试写事务，用户可在确认失败后重新提交。唯一约束和事务原子性由数据库保证，SQLITE_BUSY 本身不会绕过权限规则。关闭或回滚异常的连接不得带着未结束事务返回池中复用。

数据访问层复用一个固定的连接生命周期实现，顺序为：获取专用连接 → BEGIN IMMEDIATE → 执行业务 → COMMIT → 关闭专用连接。BEGIN 成功后立即注册延迟清理；任何业务错误、panic、请求取消或 COMMIT 失败都先尝试 ROLLBACK。清理使用独立的短超时上下文（例如 2 秒），不能复用已经取消的请求上下文；仅在确认 COMMIT 或 ROLLBACK 成功后正常归还连接。ROLLBACK 失败或无法确认事务已结束时，通过 `Conn.Raw` 回调返回 `driver.ErrBadConn`，让 database/sql 丢弃底层连接，再关闭专用连接；仅调用 `Conn.Close()` 不代表丢弃。panic 完成清理后继续传播。测试以故障注入验证回滚失败的连接不会被下次请求复用，不能只测试正常提交。

`admin init`、`recover-password` 和迁移均要求先停止服务，不支持 CLI 与服务并行写入。同一部署只运行一个服务进程；进程内互斥不能替代数据库事务或约束。实现前验证单连接模式下不存在嵌套取连接、锁等待不受控或关闭连接泄漏。

### 4.5 页面安全响应头

实际提供 Vue 页面和静态资源的服务（生产反向代理或应用静态服务）负责设置 CSP：生产构建默认 `default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`。前端不使用内联脚本、动态代码执行或内联样式；新增外部资源时需明确调整策略。开发服务器的 HMR/WebSocket 策略单独配置，不将开发放宽项带到生产。

页面及 API 设置 `X-Content-Type-Options: nosniff`、`Referrer-Policy: strict-origin-when-cross-origin`；页面禁止被嵌入。生产 HTTPS 入口设置 `Strict-Transport-Security: max-age=31536000`，初期不加 includeSubDomains 或 preload。验收检查最终页面响应，不能只验证 API 响应头。

## 5. API 契约

所有接口前缀为 `/api`。成功返回 `{"data": ...}`，204 响应无响应体；错误统一为 `{"error":{"code":"...","message":"..."}}`。不得返回 SQL、堆栈、哈希和内部路径。

### 5.1 认证和个人设置

| 方法与路径 | 请求/响应要点 | 权限 |
| --- | --- | --- |
| `GET /auth/csrf` | 返回 `{token}`；有效匹配令牌复用，否则设置新 Cookie | 公开 |
| `POST /auth/register` | `{username,password}`；201 返回用户摘要，不自动登录 | 公开，CSRF |
| `POST /auth/login` | `{username,password}`；200 返回 `{user: 用户摘要, csrf_token}`，设置 Session 与 CSRF Cookie | 公开，CSRF |
| `POST /auth/logout` | 204，撤销会话、清理 Session Cookie、设置新匿名 CSRF Cookie；前端随后 GET /auth/csrf | CSRF，重复调用须匹配当前认证上下文 |
| `GET /me` | 返回 id、username、role、must_change_password、created_at | 登录 |
| `PUT /me/password` | `{current_password,new_password}`；204，撤销全部会话 | 登录，CSRF |
| `GET /me/preferences` | 返回完整个人设置 | 登录 |
| `PUT /me/preferences` | 完整替换，返回保存结果 | 登录，CSRF |

设置写入必须提交全部设置字段，数组可为 `[]`，营养目标可为 `null`，遗漏字段返回 400。请求不接受 `user_id`，归属来自会话。校验和保存全部成功或全部失败。首版多标签页并发设置保存采用最后一次成功写入覆盖，页面明确显示保存结果。

设置响应包含同名设置字段和只读的 `excluded_foods` 数组，元素为 `{id,name,status}`，其中 status 仅为 `active` 或 `disabled`，与公共食材状态字段一致，供页面展示停用状态；写入不接受该只读字段。已有停用引用的保存规则见 3.3 节。

设置请求示例：

```json
{
  "allergens": ["milk", "peanut"],
  "excluded_food_ids": [12, 35],
  "dietary_preferences": ["low_salt"],
  "daily_energy_kcal": 2000,
  "daily_protein_g": null,
  "daily_fat_g": null,
  "daily_carbohydrate_g": null
}
```

### 5.2 管理接口

| 方法与路径 | 请求/响应要点 |
| --- | --- |
| `GET /admin/users` | page 默认 1，page_size 默认 20、最大 100；可按用户名、role、status 筛选；返回 items、total |
| `PATCH /admin/users/:id` | `{role?,status?}`，至少一个字段；返回更新后用户摘要 |
| `POST /admin/users/:id/reset-password` | `{temporary_password}`；204，撤销会话并设置强制改密 |
| `GET /admin/audit-logs` | 同样分页，可按目标用户、action 筛选 |

管理员重置密码时输入满足同一密码规则的临时密码，响应不回显；管理员通过约定的独立渠道交付，系统不自动发消息。用户必须登录后改密才能使用业务功能。管理员修改自己的密码走 `/me/password`。

服务端拒绝通过管理接口修改自己的 role/status 或重置自己的密码，返回 `409 SELF_ADMIN_CHANGE_FORBIDDEN`，前端隐藏操作不能替代此检查。本人改密必须校验当前密码。管理接口不允许把临时密码设置为该用户当前密码，强制改密也必须使用与临时密码不同的新密码。

任何变更都必须保证至少有一个 active admin，采用 4.4 节的立即写事务完成检查、变更、会话撤销及审计。在同一事务内再次核验操作者当前会话、active 状态、认证版本、强制改密状态和 admin 角色，防止请求通过中间件后管理员恰好被降级或禁用仍提交管理变更。

两个管理列表均按 `id DESC` 排序，使用 offset 分页；总数与页面数据在同一读事务中查询。同一次查询结果保持一致，但不同页请求之间有新增数据时仍可能重复或遗漏，首版允许刷新重新查询，不承诺快照遍历。

### 5.3 状态码和错误码

| HTTP | 错误码示例 | 处理 |
| --- | --- | --- |
| 400 | `INVALID_ARGUMENT` | 字段和格式错误 |
| 401 | `AUTH_REQUIRED` / `INVALID_CREDENTIALS` | 未登录、会话失效或凭据错误 |
| 403 | `FORBIDDEN` / `CSRF_INVALID` / `PASSWORD_CHANGE_REQUIRED` | 权限、来源或强制改密限制 |
| 404 | `NOT_FOUND` | 资源不存在或属于他人，统一响应 |
| 409 | `USERNAME_TAKEN` / `LAST_ADMIN_REQUIRED` / `SELF_ADMIN_CHANGE_FORBIDDEN` / `IDEMPOTENCY_KEY_REUSED` / `IDENTITY_CHANGED` | 唯一约束、管理规则、幂等载荷或页面身份冲突 |
| 415 | `UNSUPPORTED_MEDIA_TYPE` | 带请求体接口的 Content-Type 不受支持 |
| 429 | `RATE_LIMITED` | 限流或哈希执行队列已满，带 Retry-After |
| 503 | `DATABASE_BUSY` | 数据库锁等待超时，本次写入回滚 |
| 500 | `INTERNAL_ERROR` | 内部异常，前端保留输入并允许重试 |

登录时密码错误、用户名不存在、账号禁用统一返回 `401 INVALID_CREDENTIALS`。已登录改密时，当前密码错误返回 `400 INVALID_CURRENT_PASSWORD`，不作为会话失效处理；数据库或哈希内部错误仍返回 500，不混成密码错误。注册返回用户名冲突意味着用户名可被枚举，这是用户名注册的已知行为，不提供额外的账号存在查询接口。

## 6. 核心流程与数据隔离

### 6.1 注册

来源/CSRF/限流检查 → 参数校验 → 生成密码哈希 → 事务插入 user 和默认设置 → 提交 → 返回 201。并发重名映射为 409；任一步失败回滚，不留下无设置账号。注册后进入登录页。

### 6.2 登录和受保护请求

来源/CSRF/限流检查 → 查询用户或虚拟哈希 → 验证密码 → 事务复核状态及版本 → 创建 Session → 提交后写 Cookie。后续请求先认证，再检查强制改密及角色，最后执行业务。

### 6.3 个人数据访问

数据访问方法显式接收可信 `userID`，例如 `GetInventoryItem(ctx, userID, itemID)`。查询和修改形如 `WHERE id = ? AND user_id = ?`；更新或删除检查影响行数，未命中统一返回 404。列表、统计、导出及子资源同样带归属条件。

SQL 参数化。批量操作校验全部资源归属，在同一事务执行，不能部分成功。任何私有数据响应都不能通过传入他人 ID、食谱 ID、库存 ID 或幂等键获取。

所有要求登录的写接口必须带 `X-Expected-User-ID`，值为表单加载或操作发起时的用户 ID。缺失或格式错误返回 400；与有效 Session 的用户 ID 不同返回 `409 IDENTITY_CHANGED`，在任何业务变更前终止。此 Header 只是防止旧页面误提交的断言，不用于认证或选择数据归属，实际 userID 仍只来自 Session。客户端不能在重提旧表单时把此值自动替换为新账号；身份变化必须丢弃表单并重新加载。公开注册、登录及幂等退出不要求该 Header。

### 6.4 烹饪确认幂等契约

首版一次确认针对一道食谱的一次实际食用，生成一条 meal_logs，库存用量可包含多种食材；多道菜分别确认，暂不支持一次确认产生多条饮食记录。

`POST /api/meals/confirm` 要求 `Idempotency-Key` Header，值为 1～128 个 ASCII 字母、数字、下划线或连字符。幂等记录直接放在 meal_logs，不建独立幂等表：增加 `idempotency_key`（TEXT）和 `request_hash`（32 字节 BLOB），确认接口必须写入两者，建立 `(user_id, idempotency_key)` 唯一约束。预留给非烹饪手工记录时两者均可空，CHECK 约束保证同时为空或同时有效，不能部分填写。meal_logs.id 就是重放返回的结果标识，与扣库存和营养快照在同一事务提交。

规范化载荷包含食谱 ID、就餐时间、实际使用的库存及用量、实际食用份量；按库存 ID 排序、将已支持单位转为标准单位并使用确定性数值编码后计算 SHA-256，不能对原始 JSON 文本直接求摘要。拒绝重复库存项、未知字段及无法换算的单位。具体业务字段随烹饪接口实现锁定，但必须遵守同载荷比较规则。

同用户同键同载荷返回首次记录结果，不再次扣减或重新按当前食谱计算；同键不同载荷返回 `409 IDEMPOTENCY_KEY_REUSED`。首次请求失败并回滚时不占用键；成功记录与键长期保留，首版不提供物理删除。重放仍要求账号有效且通过认证/CSRF，但不将当前食材限制重新应用于已完成记录。并发相同请求由唯一约束和事务保证只执行一次。

### 6.5 推荐和营养联动

每次推荐读取当前设置；读取失败不能退化成无过敏限制。先过滤过敏和忌口，再按偏好排序；过敏原标注不完整的食谱不进入推荐。AI 替代食材必须再次经过同一规则校验。

修改设置后下一次推荐生效。首次烹饪确认在同一写事务内读取设置和待使用食谱，避免旧页面绕过新限制；确认事务校验库存归属、扣减和饮食记录写入。停用食材的已有忌口限制继续执行，不自动清理。营养目标只影响当前对比展示，不重新计算历史饮食快照。

## 7. 前端实现

新增登录页、注册页、个人设置页、修改密码页、管理员用户管理页和审计列表页。用户管理不展示用户饮食信息；角色变更、禁用和重置密码需要明确确认。

- 应用启动请求 `/me` 恢复状态；状态放在 Vue 响应式内存中，首版无需另加状态管理库。Session 不写入 localStorage。
- `api.js` 统一发送 Cookie、CSRF 和受保护写操作的 X-Expected-User-ID，解析错误。登录成功保存新 csrf_token；CSRF 失效时先重新获取令牌并用 `/me` 核对身份，再提示用户重提，不自动重放写请求。退出、改密后清空内存令牌并重新获取匿名令牌。
- 使用 `BroadcastChannel("freshplate-auth")` 在登录、退出、改密导致会话撤销后广播“身份可能变化”事件，不传密码、Cookie 或令牌；其他标签页立即暂停提交并请求 `/me`。不支持 BroadcastChannel 时不引入兼容库，依靠窗口 focus 和页面 visibilitychange 变为 visible 时的 `/me` 复核；提交前同样复核身份。
- `/me` 返回的用户 ID 与页面加载身份不同或变为未登录时，清空个人缓存、CSRF 内存值和旧表单，重新进入对应页面。身份检查失败时保持暂停提交，提供重试；即使广播延迟或复核后恰好切换账号，服务端 X-Expected-User-ID 校验也会拒绝旧表单。身份变化时递增页面请求代次，丢弃旧代次的异步响应，防止旧账号数据回填新页面。
- 路由守卫等待身份初始化完成；未登录进入登录页，回跳路径只接受本站内部路径，防止开放重定向。
- `must_change_password=true` 时进入改密页面；401 清空身份并进入登录，403 根据错误码提示改密或无权限。
- 表单保留失败输入但不持久化密码；密码框设置正确的 autocomplete。提交期间禁用按钮，提供可访问标签、字段错误与键盘操作。
- 设置加载失败不展示伪造默认值供保存；保存失败保留编辑内容。过敏、忌口与排序偏好分开说明。
- 页面展示用户及审计字符串使用 Vue 默认转义，不使用 `v-html`。

## 9. 初始化、迁移与恢复

管理员命令及迁移执行前必须停服务，完成后再启动。初始化流程由显式本地命令驱动，不能在公开注册接口或 HTTP 启动路径自动创建管理员。CLI 的创建、查找及旧数据归属账号统一复用 3.1 节的用户名规范化与合法性校验，不因命令入口不同创建大小写重复账号或查不到同一账号。

### 9.1 首个管理员

本地 `admin init` 命令在没有管理员时创建首个 active admin，同时创建默认设置并写审计。密码从隐藏终端输入获取，不通过命令行参数、日志或提交到仓库的配置传递。已有管理员时拒绝重复初始化；绝不将第一个公开注册用户自动提升为管理员。

### 9.2 本地恢复

`admin recover-password --username <name>` 仅用于已有 active admin，由拥有服务器与数据库访问权的运维人员执行；隐藏输入临时密码，增加版本、删除会话、设置强制改密并写审计。不通过此命令恢复已禁用账号或任意提升角色。

### 9.3 数据迁移

当前尚无业务数据库，实现时直接创建包含 user_id 的最终表结构。若实施过程中已产生单人数据，则按以下步骤迁移：

1. 停止服务，备份 SQLite 数据库及现有 CSRF 密钥，运行完整性和外键检查。使用 SQLite 一致性备份方式或确认 WAL 已完整 checkpoint 后复制主库，不能遗漏未合并的 WAL 数据。
2. 本地迁移命令隐藏读取初始管理员密码并明确旧数据所有者，事务外生成哈希；不能自动归属给第一个注册者。已有管理员时选择有效账号，不重复初始化。
3. 专用连接在事务外关闭 foreign_keys，然后 BEGIN IMMEDIATE。事务内创建认证表、所需初始账号、默认设置和初始化审计，将库存、饮食记录、旧 preferences 和私有食谱归属到指定账号；公共食材和人工公共食谱保持共享。导入旧设置覆盖该所有者的默认设置，不产生第二条。
4. 按依赖关系先建立新父表，再复制子表；在同一事务内重建业务表、恢复索引和触发器、校验行数与归属，并执行 foreign_key_check，必须无违规记录。
5. 同一事务写入 schema_migrations 版本及脚本校验值后提交；失败回滚。最后在事务外恢复 foreign_keys=ON 并复核，失败不得启动服务。该迁移包含初始化账号所需步骤，不提前运行只适用于最终结构的 admin init。
6. 使用所有者账号检查库存和记录，再用第二个账号验证不可见。

空数据库使用同一迁移入口直接创建最终结构，完成后运行 admin init。`schema_migrations` 保存版本、脚本校验值和完成时间；程序启动若发现数据库版本比支持版本新、已应用脚本校验值不符或迁移不完整，拒绝启动。

不做自动降级删除用户列。需要回退时停止服务，配套恢复迁移前数据库、密钥与旧程序；明确迁移后新增数据不能直接用旧备份保留。

## 12. 已知限制

- 固定两种角色适用于当前规模；需要家庭共享或细粒度授权时再设计资源成员关系，不复用管理员权限绕过归属。
- SQLite 单连接和内存限流面向单实例；多实例或较高写并发时，需重新验证连接池、数据库、会话与共享限流方案。CLI 维护要求停服务。
- Session 固定 7 天到期，令牌泄露后在撤销或到期前可能被使用；首版不增加空闲超时、周期轮换或会话数量管理。
- 公开注册、长期保留审计、offset 翻页均采用上述明确边界；限制注册、自动归档或快照遍历应在出现实际需求时单独实现。
- 无邮箱/短信意味着普通用户依赖管理员恢复账号。知道临时密码的应用管理员可以登录并接管目标账号，因此本方案信任管理员，不提供对恶意管理员的数据机密性保护；审计只能追责，不能阻止接管。若产品要求抵御此威胁，需要重新设计管理员不能单独完成的恢复流程（如用户持有恢复凭据或双人审批），不能只保留强制改密。
- 服务器管理员仍可访问数据库文件，应限制操作系统访问和备份权限；应用层授权不能替代服务器管理者的信任边界。
- 食谱过敏原标注和食材归类质量决定过滤覆盖程度，系统不能承诺消除过敏风险。
