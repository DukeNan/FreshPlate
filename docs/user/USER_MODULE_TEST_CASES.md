# 用户模块测试用例与需求追踪

> 认证已迁移到 JWT；本文保留早期设计和验证背景。当前认证契约、迁移与测试范围以 [JWT 认证说明](JWT_AUTHENTICATION.md) 和 [API 文档](API.md) 为准。

后续执行记录见 [实施与测试总结](USER_MODULE_IMPLEMENTATION_SUMMARY.md) 及 [正式实施方案](USER_MODULE_TEST_EXECUTION_PLAN.md)；下文“未执行”为用例编写时的初始状态。

## 1. 基线、范围与执行状态

依据：[用户模块技术设计](USER_MODULE_TECHNICAL_DESIGN.md)、[实施方案](../../IMPLEMENTATION_PLAN.md)。编写时仓库只有方案与评审文档，没有 `server/`、`web/`、业务数据库或可运行测试。本文件是待实现用例，不是执行记录；全部用例初始状态均为 **未执行**，不能据此宣称安全验收通过。

范围标记：

- **U（当前必实现）**：用户、Session、密码、CSRF、权限、个人设置、管理、CLI、数据库基础、对应前端与本机交付。
- **B（后续强制验收）**：库存、公共食材维护、食谱、推荐、AI、记餐、营养等尚不存在的业务功能。该模块一旦新增入口，必须执行相应矩阵；不存在的入口不能以空测试通过。
- **C（条件验收）**：遗留单人数据库迁移、生产 HTTPS 部署。条件不具备时明确阻塞条件；不能计入已通过。空库建表、迁移版本检查和事务故障属于 U。

U 中忌口 ID 校验需要最小公共食材数据契约（`id/name/status`）及真实数据库夹具；不要求为测试扩大实现为完整食材维护模块。如本轮不实现食材目录 UI，应记录其阻塞影响，不能省略后端设置规则。

架构对应：HTTP/前端负责契约和交互，logic 负责密码与固定业务规则，store 负责归属、事务和数据库约束；测试同时验证接口结果和真实落库状态，不能只验证中间件 mock。

## 2. 共用前置、执行约定与证据

后端使用标准 `testing`、`httptest`、临时 SQLite **文件**；每例独立数据库、Cookie jar、可控时钟。前端使用仓库最终选定的交互测试工具；未选定前标记工具待定，不臆造可执行 npm 脚本。浏览器人工测试不能替代后端并发和故障测试。

固定夹具：普通用户 A、B；active 管理员 M1、M2；禁用用户 D；强制改密用户 F。各账号用户名和密码不同；按需为每人建立两个 Session。A/B 各有个人设置；B 范围另建分别归属 A/B 的库存、私有食谱及子资源、饮食记录，已发布/未发布公共食谱，active/disabled 食材。基准 Origin 为实际配置的精确源，测试用 HTTP Cookie 名；HTTPS 分支另用 TLS 服务。

默认已认证写请求步骤：获取该 Session 绑定的 CSRF → 携带 Cookie、精确 Origin、`X-CSRF-Token`、表单加载时的 `X-Expected-User-ID` 和 JSON。公开注册/登录以及退出不要求 Expected Header。负例每次仅改变目标变量，避免被其他校验提前拦截而形成假阳性。

每行均给出前置/操作/断言；矩阵每个参数单独形成子用例（例如 `CSRF-003/expired`），保留父 ID。HTTP 错误校验状态、错误码、无敏感细节；所有拒绝写入用例同时比较业务表、Session、认证版本和审计的前后状态。设计没有承诺具体错误码的内部故障，不自行增订接口，按 500/503 的实际契约验证。

并发用屏障或受控 hook 固定到“哈希完成”“中间件已通过”“事务未提交”等位置，释放后检查最终状态；不得依赖 `sleep` 侥幸触发竞态。真实 SQLite 负责并发和原子性验证，驱动故障注入只补充 COMMIT/ROLLBACK 等难稳定触发的路径。

层次：**L**=纯逻辑单元，**S**=真实 SQLite 集成，**H**=HTTP 集成，**F**=前端交互，**E**=真实浏览器端到端，**O**=运维/部署演练，**R**=代码审查（如常量时间比较、秘密不落盘）。每条证据应记录子用例 ID、提交版本、命令/操作、时间、预期/实际、结果与脱敏产物路径；结果仅可为未执行、通过、失败、阻塞或不适用（附条件），不可将“未发现”写成通过。
