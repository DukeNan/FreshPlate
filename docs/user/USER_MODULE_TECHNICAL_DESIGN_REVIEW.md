## 1. 总体评价

方案整体质量较高，安全模型方向正确，主要亮点包括：

- 采用服务端 Session + HttpOnly Cookie，不引入 JWT，会话可撤销，符合当前单实例部署规模。
- `auth_version` 机制同时覆盖会话撤销和“旧密码校验完成后恰逢重置”的竞态，设计严谨。
- 个人设置读取失败时 fail-closed，不退化为“无过敏限制”，符合食品安全类业务的正确默认值。
- 所有业务查询显式接收可信 `userID`，并同时约束资源 ID 与归属，隔离思路正确。
- 最后管理员保护、管理变更与审计同事务、审计脱敏等管理面规则完整。
- 测试矩阵覆盖面较好，已包含并发、迁移、双用户越权和请求安全。

需要修正的问题集中在四处：CSRF 在多标签页下的契约、私有食谱发布语义、SQLite 写并发的可执行配置、以及若干边界规则缺失。这些问题不会推翻整体架构，但必须在编码前写清楚，否则不同实现者会得出不同行为。

## 3. P0：冻结接口前必须解决

### P0-01 CSRF 双提交 Cookie 与多标签页/登录轮换冲突

**现状**

`docs/user/USER_MODULE_TECHNICAL_DESIGN.md:120-132` 规定：

- CSRF Cookie 为 host-only、`HttpOnly`、`SameSite=Lax`、`Path=/`；
- 前端把 token 保存在内存，写请求通过 `X-CSRF-Token` 发送；
- 后端比较 Header 与 Cookie；
- 登录后轮换 CSRF token。

**问题**

Cookie 在同源的所有标签页之间共享，而每个标签页只持有自己内存中的 token。只要出现第二次 `/auth/csrf` 调用，就会覆盖 Cookie：

1. 标签页 A 调用 `/auth/csrf`，Cookie=`T1`，A 内存中保存 `T1`。
2. 标签页 B 调用 `/auth/csrf`，服务端生成 `T2` 并覆盖 Cookie。
3. 标签页 A 提交写请求：Header=`T1`，Cookie=`T2`，必然返回 `CSRF_INVALID`。

登录后轮换也会让其他标签页内存中的 token 立即失效。当前文档没有定义刷新机制，只写了“CSRF 失效时提示重新提交”（`:226`），实现时容易出现“每次打开新标签页就破坏已有标签页写操作”的问题。

**建议**

采用“幂等获取 + 登录轮换”的组合：

- `GET /auth/csrf` 幂等：请求若携带有效且未过期的 CSRF Cookie，直接返回该 Cookie 的值，不生成新 token；无有效 Cookie 时才生成并设置。
- 登录成功时轮换 token，并在登录响应体中返回新 token；前端必须用响应值更新内存。
- 收到 `CSRF_INVALID` 时，前端重新调用 `/auth/csrf` 更新内存，再提示用户重新提交；不自动重放写请求。
- 更彻底的方案是登录后把 token 绑定到 Session：`token = HMAC(key, "csrf" || session_token_hash)`，同一 Session 的所有标签页天然共享同一 token；登录前使用独立的匿名 token。

**建议文档修改**

将 `4.3` 中 CSRF 部分改为：

```text
- GET /api/auth/csrf 幂等：若请求携带有效未过期的 CSRF Cookie，返回该 Cookie 的值；
  否则生成新令牌、设置 Cookie，并在响应体返回同一令牌。
- 登录成功后轮换 CSRF 令牌，并在登录响应体中返回新值。
- 前端收到 CSRF_INVALID 后重新调用 /auth/csrf，更新内存并提示用户重新提交；
  不自动重放写请求。
```

### P0-02 私有食谱“发布”与管理员不可读原则冲突

**现状**

- `:38`：管理员没有默认读取他人私有食谱的特权。
- `:102`：`recipes` 增加 `owner_user_id` 和 `visibility`；公共食谱只有管理员能创建或发布。

**问题**

如果管理员可以把任意用户的私有食谱改为 `public`，则“发布”操作必须先读取内容，直接违反前者。此外文档没有定义：

- 发布后 `owner_user_id` 是否保留；
- 原作者是否仍能编辑已发布食谱；
- 原作者编辑后是否绕过管理员审核；
- 管理员能否撤回他人的公共食谱。

**建议**

明确以下规则：

1. 公共食谱由管理员创建和维护，`owner_user_id` 为空或为管理员。
2. 普通用户只能提交“发布申请”，不能直接发布；管理员发布时复制一份独立的公共食谱，原私有食谱保留并继续归用户所有。
3. 用户不能编辑或撤回已发布的公共副本。
4. 若未来允许“发布后仍由作者维护”，必须单独定义审核与撤权流程，首版不实现。
5. 数据约束补充：

```sql
CHECK (visibility IN ('private','public')),
CHECK (visibility = 'public' OR owner_user_id IS NOT NULL)
```

### P0-03 SQLite 写并发缺少可执行配置

**现状**

`:183` 要求“SQLite 使用立即写事务或等效的写锁策略”，但没有给出驱动、连接池和事务的具体配置。

**影响**

以下不变量全部依赖写操作被正确串行化：

- 最后一个 active admin 的保护；
- 登录成功时复核状态、版本与密码哈希；
- 改密/重置与旧密码校验的竞态；
- 幂等键唯一约束；
- 管理变更与审计同事务。

如果只是“检查后再更新”，在 `database/sql` 默认的 deferred 事务下，升级写锁时可能直接得到 `SQLITE_BUSY`，导致上述保护出现绕过或返回 500。

**建议**

在文档中明确：

1. 连接 DSN 必须为**每个连接**设置 `foreign_keys` 和 `busy_timeout`，并建议启用 WAL。示例（需按 `modernc.org/sqlite` 实际支持的参数验证）：

```text
file:data/freshplate.db?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=journal_mode(WAL)
```

2. 确认驱动是否支持 `_txlock=immediate`；若不支持，所有“检查后更新”的事务必须显式执行 `BEGIN IMMEDIATE`（通过专用 `*sql.Conn`），或在进程内用写互斥串行化。不能依赖默认的 deferred 事务。
3. 明确 `SetMaxOpenConns` 上限。WAL 下允许多读单写，但连接数过多会造成写饥饿；建议给出初始值和压测方式。
4. 明确 `admin init` / `recover-password` 与服务同时运行时的行为。建议首版要求先停止服务；若允许并发执行，必须统一处理 `busy_timeout` 和重试，并写入文档。
5. 迁移重建表时，`PRAGMA foreign_keys=OFF` 必须在事务外设置；重建完成后执行 `PRAGMA foreign_key_check`，再恢复 `ON`。SQLite 的 DDL 本身在事务内，迁移应整体提交或回滚。

### P0-04 Origin、Content-Type 与 CORS 边界未定义

**现状**

`:131-132` 只写了“仅接受 JSON 请求和配置中精确匹配的站点 Origin”，未定义缺失 Origin、`Origin: null`、CORS 和 Content-Type 的具体处理。

**建议**

补充以下规则：

- 所有 `POST/PUT/PATCH/DELETE` 请求必须携带 `Content-Type: application/json`，拒绝 `text/plain`、`application/x-www-form-urlencoded`、`multipart/form-data`。
- `Origin` 必须存在且与配置的应用源完全一致（scheme + host + port）；缺失或为 `null` 一律返回 `403 CSRF_INVALID` 或独立的 `ORIGIN_INVALID`。
- 首版不启用 CORS。Vite 开发代理是同源访问，不需要 CORS；将来若启用，必须使用显式允许列表并允许凭据，禁止 `*`。
- Origin 比较使用配置值，不从 `Host` 或 `X-Forwarded-*` 推断。
- 明确反向代理场景下仅信任配置的代理地址，与 `:136` 的 Gin 信任代理规则保持一致。

### P0-05 “所有主键为 INTEGER”与 `sessions` 表矛盾

**现状**

- `:44`：所有主键使用 SQLite `INTEGER PRIMARY KEY`。
- `:65`：`sessions.token_hash` 为 `BLOB PRIMARY KEY`。

**建议**

二选一，并在全文保持一致：

- 方案 A（推荐）：`sessions` 改为：

```sql
id INTEGER PRIMARY KEY,
token_hash BLOB NOT NULL UNIQUE,
```

- 方案 B：把总述改为“除 `sessions` 使用令牌摘要作为主键外，其余主键使用 `INTEGER PRIMARY KEY`”。

## 4. P1：编码前应确定

### P1-01 CSRF token 未绑定会话/用户

当前 token 由随机数、签发时间和 HMAC 组成，任意用户的合法 token 在所有会话中都可被接受。host-only Cookie 已显著降低风险，但绑定 Session 的成本很低。建议登录后把 token 绑定到 `session_token_hash`；登录前使用独立的匿名 token，仅用于注册/登录/退出。

### P1-02 Session 生命周期策略

`:69` 规定固定 7 天到期、不续期；`:71` 规定启动时及每小时清理。建议补充以下决策：

- 是否接受“令牌被盗后最长 7 天有效”的风险；
- 是否增加空闲超时（例如 24 小时）并在访问时低频续期（例如每小时最多写一次）；
- 是否限制每用户会话数量（例如 10 个），登录时淘汰最旧会话；
- 角色变更后是否要求重新登录。当前“每次读取当前角色”已保证立即生效，可以不改，但应明确。

若首版坚持固定 7 天，建议在“已知限制”中写明该权衡，而不是留白。

### P1-03 `PUT /me/password` 缺少限流

攻击者取得会话后可以对当前密码进行暴力尝试。建议增加按用户和按 IP 的限流（例如每 15 分钟 5 次），返回 `429 RATE_LIMITED`，失败响应不区分“当前密码错误”与其他内部错误。

### P1-04 缺少安全响应头

除 `Cache-Control: no-store` 外，建议补充：

- `Content-Security-Policy`（禁止内联脚本，前端构建产物使用外链资源）；
- `X-Frame-Options: DENY` 或 CSP `frame-ancestors 'none'`；
- `X-Content-Type-Options: nosniff`；
- `Referrer-Policy`；
- HTTPS 部署时启用 HSTS。

### P1-05 注册开放策略与部署边界

`:23` 允许在安全验收后通过 HTTPS 反向代理提供网络访问，但 `POST /auth/register` 永远开放。若服务提供给家庭或局域网使用，任何可达用户都能注册。建议：

- 增加 `registration_enabled` 配置，默认关闭或仅在环回地址监听时开启；
- 或采用邀请码；
- 至少在监听非环回地址时输出启动警告，并写入“已知限制”。

### P1-06 偏好中引用已停用食材

`:79-87` 只说明“被引用的食材不物理删除，采用停用”，但没有定义读取行为。建议：

- 写入时：所有 `excluded_food_ids` 必须存在且为 active 公共食材，否则 400；
- 读取时：保留原值，不因某个食材停用而使整个设置读取失败；可返回可用性标记供前端提示；
- 推荐时：忽略已停用项，但相关过敏/忌口限制不能因此放宽；
- 下次保存时由前端或后端清理失效 ID。

### P1-07 审计日志保留策略

`:93-97` 未定义保留期限。长期运行会无限增长。建议明确：

- 首版只增不删，写入“已知限制”；
- 或定义保留窗口（例如 180 天）并说明清理方式；
- 无论哪种，都不提供网页修改/删除入口。

### P1-08 迁移执行细节

`:279-288` 已给出步骤，但需要落到可执行层面：

- 增加 `schema_migrations` 表，记录版本和校验值；
- 程序启动时若数据库版本高于二进制支持版本，拒绝启动，防止旧程序打开新库；
- 备份内容必须包含 SQLite 数据库和 CSRF 密钥文件；
- 明确重建表顺序、外键开关时机、`foreign_key_check` 和行数校验；
- 明确失败回滚时恢复旧二进制和数据库，迁移后新增数据不会自动回到旧备份；
- 明确 `admin init` 在迁移流程中的执行位置。

### P1-09 幂等键契约

`:105` 只规定唯一约束。建议补充：

- 幂等键必填，长度和字符集限制（例如 1～128 个可见 ASCII 字符）；
- 同用户、同键、同载荷重复提交返回首次结果（或明确返回 `409`）；
- 同用户、同键、不同载荷返回 `409 IDEMPOTENCY_KEY_REUSED`；
- 幂等键不跨用户共享；
- 需要保存首次请求的结果标识（例如 `meal_log_id`），以便重放返回一致结果。

### P1-10 管理员对自身执行管理操作的拒绝

`:181` 说明管理员修改自己的密码应走 `/me/password`，但未明确服务端必须拒绝：

- `POST /admin/users/:id/reset-password` 中 `:id` 等于当前管理员；
- `PATCH /admin/users/:id` 中修改自己的 `role` 或 `status`。

建议统一返回 `409 SELF_ADMIN_CHANGE_FORBIDDEN`，并确保前端隐藏按钮只是交互层，服务端必须独立校验。

## 5. P2：建议澄清

| 编号 | 建议 |
| --- | --- |
| P2-01 | 明确密码按原始码点比较，不做 NFC/NFKC 规范化；避免不同客户端组合字符导致“看起来一样但登录失败”。 |
| P2-02 | `GET /admin/users` 和 `GET /admin/audit-logs` 指定稳定排序，例如 `ORDER BY id DESC`，避免并发写入时翻页重复或遗漏。 |
| P2-03 | 明确 `429 RATE_LIMITED` 同时覆盖限流和哈希队列满，或增加 `HASH_QUEUE_FULL` 便于运维区分；两者都应返回 `Retry-After`。 |
| P2-04 | 明确 CSRF Cookie 名称；HTTPS 部署建议使用 `__Host-` 前缀，防止共享父域下的 Cookie 覆盖。 |
| P2-05 | `:132` “命令行管理员工具直接调用本地应用逻辑，不绕过 HTTP 来源校验”表述矛盾。建议改为“CLI 不暴露任何网络旁路，直接以本地运维权限操作数据库，并写入审计”。 |
| P2-06 | `409 SELF_ADMIN_CHANGE_FORBIDDEN` 与 `403 FORBIDDEN` 的语义边界建议统一：管理规则冲突用 409，纯权限不足用 403。 |
| P2-07 | CSRF Header 与 Cookie 的比较建议使用常量时间比较，避免不必要的实现差异。 |

## 6. 建议补充的测试用例

在 `:294-307` 的矩阵基础上增加：

| 范围 | 补充场景 |
| --- | --- |
| CSRF | 多标签页交替调用 `/auth/csrf` 后写请求仍成功；登录轮换后旧 token 失效、新 token 生效；缺失 Origin、`Origin: null`、非 JSON Content-Type 均被拒绝 |
| 会话 | 同一用户多会话上限；固定到期与空闲超时（若实现）；会话令牌不出现在日志 |
| SQLite | 并发写触发 `SQLITE_BUSY` 时重试或明确失败；CLI 与 server 同时运行的行为；迁移期间外键检查 |
| 管理 | 管理员对自己重置密码/改角色/改状态被服务端拒绝；重置他人密码不影响最后管理员约束 |
| 食谱 | 管理员不能读取或发布他人私有食谱；用户提交发布申请后原私有食谱仍不可公开访问 |
| 偏好 | 引用已停用食材时的读取与保存行为；推荐不会因停用数据放宽限制 |
| 幂等 | 同键同载荷返回首次结果；同键不同载荷返回 409；不同用户同键互不影响 |
| 迁移 | 数据库版本高于程序版本时拒绝启动；迁移失败后旧程序可基于备份恢复 |
| 响应头 | CSP、`frame-ancestors`、`nosniff`、HSTS（HTTPS）存在且配置正确 |

## 7. 待产品/运维确认的问题

以下问题不是文档缺陷，但会影响实现取舍，建议在设计冻结前确认：

1. 首版是否只允许本机环回访问？若允许家庭/局域网访问，注册是否需要邀请码或管理员开关？
2. 公共食谱是否允许来源于用户提交？若允许，采用“复制为公共副本”还是“作者保留编辑权 + 审核”？
3. 固定 7 天会话是否可接受？是否需要空闲超时或更短的有效期？
4. 审计日志是否需要保留期限？若不清理，磁盘容量如何监控？
5. 管理员重置密码后的临时密码通过什么独立渠道交付？是否需要记录交付责任人？
6. `admin init` / `recover-password` 是否允许在服务运行时执行？建议要求先停服务。

## 8. 修订优先级与建议动作

1. **先修 P0-01 至 P0-05**：CSRF 契约和 SQLite 事务策略会直接影响代码结构，必须在接口冻结前确定。
2. **再补 P1-02、P1-05、P1-08**：会话生命周期、注册策略和迁移细节影响部署与运维。
3. **P1 其余项和 P2** 可作为实现阶段的 checklist，不阻塞设计冻结。
4. 按第 6 节补充测试矩阵，尤其是多标签页 CSRF、CLI 并发写和迁移降级保护。
5. 更新 `IMPLEMENTATION_PLAN.md` 中与注册策略、部署边界相关的描述，保持两份文档一致。

## 9. 评审结论

方案可以作为 FreshPlate 用户模块的实现基线。核心安全模型、数据隔离和审计设计无需推翻；需要的是把若干隐含前提写成明确规则，尤其是：

- CSRF token 在多标签页和登录轮换下的获取/刷新契约；
- 私有食谱发布的隐私边界；
- SQLite 写事务的驱动级配置；
- Origin/Content-Type/CORS 的拒绝规则；
- 主键约定的内部一致性。

完成上述 P0 修正后，即可冻结第 5 节 API 契约，进入前后端并行开发。
