## 1. 复审结论

本轮更新的质量较高，不是简单打补丁，而是把上轮指出的隐含前提写成了明确规则：

- CSRF 改为“幂等获取 + 登录轮换 + Session 绑定 + 失效恢复”，并补充了登录响应 `csrf_token` 和多标签页恢复流程。
- 私有食谱改为管理员独立维护公共食谱，明确不提供私有转公共、投稿和审核，消除了隐私模型冲突。
- 新增 `4.4 SQLite 连接及事务策略`，明确单连接池、逐连接 PRAGMA、手写 `BEGIN IMMEDIATE`、`503 DATABASE_BUSY` 和 CLI 停服务要求。
- Origin、Content-Type、CORS、`__Host-` Cookie、安全响应头、注册开放性、停用食材、审计保留、迁移细节和幂等契约均已补齐。
- 测试矩阵同步扩展，覆盖 CSRF 复用/跨会话/多标签页、SQLite 单连接、迁移版本保护和最终页面响应头。

**上轮 5 项 P0 全部闭环。** 10 项 P1 中 9 项闭环，1 项（Session 生命周期）以“明确接受限制”的方式闭环。P2 基本闭环。

本轮新发现的问题不再是架构级问题，主要是边界规则和威胁模型需要进一步明确。其中 3 项建议在编码前定稿。

## 3. 本轮新发现

### R2-01（P1）`/auth/csrf` 的“认证上下文”必须按数据库中的有效 Session 判定

**位置**：`:136-138`、`:141`、`:176`

**现状**

文档规定：

- 已认证 CSRF 令牌的 HMAC 输入包含当前 Session 的 `token_hash`；
- `/auth/csrf` 若 Cookie 中令牌有效、未过期且“与当前认证上下文匹配”，复用该值；
- Session 失效后不能再用其令牌访问受保护接口。

**风险场景**

Session 过期、被登出或被改密/重置删除后，浏览器中仍可能保留 Session Cookie 和 CSRF Cookie。此时如果 `/auth/csrf` 仅通过“Cookie 存在 + HMAC 可验证”判断认证上下文，就会返回绑定已失效 Session 的已认证令牌。后续登录请求按匿名上下文校验，令牌用途不匹配，返回 `CSRF_INVALID`；前端按 `:140` 重新获取，仍得到同一个已认证令牌，形成循环，用户无法重新登录。

这不是理论问题：改密成功会删除全部 Session，但浏览器不会自动清除 Session Cookie；Session 过期时 Cookie 也可能仍在有效期内。

**建议**

明确“认证上下文”与认证中间件完全一致，至少包括：

- Session 记录存在；
- `expires_at` 未到期；
- 用户 `status = active`；
- `sessions.auth_version = users.auth_version`。

只有全部满足才复用绑定该 Session 的已认证令牌；否则一律按匿名上下文处理，生成匿名令牌、覆盖 CSRF Cookie 并返回。

**建议补充测试**

- 登录后从数据库删除 Session（或改密/重置），再调用 `/auth/csrf`，必须返回匿名令牌，且用该令牌可以重新登录。
- Session 过期但 Cookie 仍存在时，同样返回匿名令牌。
- 登出后调用 `/auth/csrf`，不得复用已认证令牌。

### R2-02（P1）管理员重置密码等价于账号接管，威胁模型需显式承认

**位置**：`:40`、`:210-212`、`:380`

**现状**

- 权限表允许管理员重置任意用户密码（`:37`）。
- `:40` 表述“管理员没有默认读取他人饮食记录、库存、过敏信息或私有食谱的特权”。
- 重置流程中管理员自选临时密码，用户登录后强制改密。

**风险**

管理员知道临时密码，可以：

1. 用临时密码登录该用户；
2. 在强制改密页面把密码改为自己知道的新密码；
3. 以该用户身份访问库存、饮食记录、过敏信息和私有食谱。

因此“管理员没有默认读取他人数据的特权”在技术上只表示“没有直接查询接口”，并不构成对恶意管理员的隔离。这是密码重置机制的固有权能，不是实现缺陷，但当前文档没有在威胁模型或已知限制中说明。

此外，`:212` 要求“临时密码不得等于该用户当前密码”，服务端需要通过 Argon2 校验当前哈希；这等于给管理员提供了一个密码验证 oracle。虽然管理员本来就能接管账号，风险有限，但如果产品真的把“管理员不可读用户数据”当作安全边界，这个检查与整个重置机制都需要重新设计。

**建议**

明确产品选择，写入威胁模型或已知限制：

- **方案 A（当前设计）**：管理员是受信任角色；重置密码等价于账号接管；通过审计、强制改密和操作确认降低误用，但不承诺对恶意管理员隔离用户数据。建议同时在 `:40` 把“没有默认读取特权”改为“不提供直接读取入口，但重置密码可导致账号接管”。
- **方案 B（更强隔离）**：引入用户持有的恢复码、分离“用户管理”和“密码重置”权限，或要求双管理员审批。固定两角色模型下这会增加明显复杂度，首版不建议。

**建议补充测试/文档**

- 审计记录必须包含重置操作、操作者和目标用户。
- 明确管理员重置后原密码立即失效、用户全部会话被撤销。
- 如保留“临时密码不得等于当前密码”，在文档中说明其安全含义，避免被误认为管理员无法获知用户密码。

### R2-03（P2）登出幂等与 Session 绑定 CSRF 的交互需说清

**位置**：`:132`、`:137`、`:177`

**现状**

- 登出要求 CSRF；
- 已认证令牌绑定 Session；
- 登出后 Session 删除；
- 文档说“已退出时仍返回成功”，同时又说“无会话退出时可先获取匿名令牌”。

**问题**

用户登出后，内存中的 token 仍绑定已删除的 Session。若再次调用登出而不先获取匿名令牌，会因用途不匹配返回 `CSRF_INVALID` 而不是 204。“可重复调用”在 API 表中容易被理解为无需额外步骤。

**建议**

二选一：

- 登出响应同时清理或轮换 CSRF Cookie 为匿名令牌（204 仍可设置 Cookie），使重复登出可以直接使用新令牌；
- 或在 API 表中明确“重复调用需先获取匿名 CSRF 令牌”，并让 `api.js` 在登出后清空内存 token、按需获取匿名令牌。

无论哪种，都建议补充“登出两次”和“Session 过期后登出”的测试。

### R2-04（P1）多标签页身份变化缺少检测机制

**位置**：`:269`

**现状**

文档要求“其他标签页发现身份变化时丢弃旧表单并重新加载，不能将上一账号的数据提交到新账号”。

**问题**

只写了要求，没有定义“如何发现”。Session 是共享 Cookie，标签页 A 中保存的是用户 A 的表单；标签页 B 登出并以用户 B 登录后，标签页 A 的表单若提交，请求会以用户 B 的身份写入，造成跨账号数据污染。

**建议**

明确一种机制：

- 登录/登出时通过 `BroadcastChannel` 广播用户 ID 和认证版本变化，其他标签页清空身份、表单缓存并重新加载；
- 或在 `visibilitychange`/`focus` 时调用 `/me`，与当前内存中的用户 ID 比较，不一致则丢弃表单；
- 任意 401 都清空身份并跳转登录。

`BroadcastChannel` 不涉及持久化 Session，和“Session 不写入 localStorage”不冲突。建议补充前端测试：两个标签页、切换账号、旧表单不得提交。

### R2-05（P2）手写 `BEGIN IMMEDIATE` 的连接生命周期需要固定模板

**位置**：`:152-158`

**现状**

文档正确要求：不要在事务内通过 `*sql.DB` 取第二条连接；异常连接不得带着未结束事务返回池中；单连接模式要验证无嵌套死锁。

**仍需明确**

手写 `BEGIN IMMEDIATE` 时，`database/sql` 不知道事务已经开始。如果 COMMIT/ROLLBACK 失败后直接 `conn.Close()`，连接可能带着打开的事务回到池中，后续请求继承该事务，看到锁或未提交数据。

建议在文档中补充固定实现模板：

- 数据访问层提供 `withImmediateTx(ctx, fn)`，统一负责获取 `*sql.Conn`、`BEGIN IMMEDIATE`、COMMIT/ROLLBACK、`defer conn.Close()`；
- 任何错误路径都必须执行 ROLLBACK；ROLLBACK 失败时丢弃底层连接，不能归还池中；
- 为获取连接和事务设置 context 超时，避免单连接被长期占用时无限等待；
- store 方法接受 `*sql.Conn` 或一个最小 `DBTX` 接口（`ExecContext`/`QueryContext`/`QueryRowContext`），确保事务内不会回退到 `*sql.DB`。

建议增加故障注入测试：BEGIN 后返回错误、ROLLBACK 失败、事务期间 context 取消，验证下一个请求不会看到未结束事务。

### R2-06（P2）幂等记录的落表方式未定义

**位置**：`:109`、`:250-256`

**现状**

文档要求保存幂等键、规范化载荷摘要和首次生成的 `meal_log_id`，唯一约束按 `(user_id, idempotency_key)` 建立，但没有说明这些字段放在 `meal_logs` 还是独立表。

**建议**

先确认烹饪确认与 `meal_logs` 的基数：

- 一次确认只生成一条 `meal_log`：可在 `meal_logs` 上增加 `idempotency_key`、`payload_digest`，并建立 `UNIQUE(user_id, idempotency_key)`；
- 一次确认生成多条记录：应使用独立的 `meal_confirm_keys` 表，保存键、摘要、首次响应引用或 `meal_log_id` 列表，避免把幂等键重复写到每条记录。

无论哪种，都需要在文档中明确，因为它直接影响迁移脚本和重放响应契约。

| 管理员重置 | 重置后旧密码失效、所有会话撤销、强制改密生效；管理员无法通过管理接口重置自己；审计记录完整 |
| 事务模板 | BEGIN 后业务错误回滚；ROLLBACK 失败不污染连接池；context 取消；单连接下无嵌套取连接 |
| 幂等 | 幂等记录的落表结构；同键同载荷重放；同键不同载荷 409；首次失败不占键 |
| 响应头 | 登录/注册/登出/`/auth/csrf` 均为 `no-store`；生产 HTML 的 CSP 阻止内联脚本和样式；HSTS 仅在 HTTPS |
| 配置 | 数据库目录锁；CLI 与 HTTP 用户名规范化一致；Origin 配置格式校验 |
| 数据库忙 | 锁等待超时返回 503 且无部分写入；前端提示重试 |

## 5. 最终结论

更新后的方案已经解决了上轮所有阻断问题，架构和安全模型无需再调整，**可以进入实现阶段**。建议按以下顺序完成最后的澄清：

1. **R2-01（必须）**：把 `/auth/csrf` 的认证上下文判定写成“与认证中间件一致的有效 Session”，否则会话失效后的重新登录可能被 CSRF 死循环阻塞。
2. **R2-02（产品决策）**：明确管理员重置密码等价于账号接管，更新威胁模型或已知限制；如果不接受，需要重新设计恢复机制。
3. **R2-04（前端实现前）**：确定多标签页身份变化的检测机制，避免跨账号表单提交。
4. R2-03、R2-05、R2-06、R2-07 可在编码前或编码中补齐，不阻塞主线。

完成上述 1～3 项后，本文可以作为前后端并行开发的最终契约。
